# 发布与兼容契约（Release & Compatibility Contract）

> 本文件是 CI 公共模板库对**业务侧的对外契约**与**内部发布纪律**。目标只有一个：
> **业务侧对模板库的变更「零感知」**——模板可以高频优化，但业务侧基本不需要被动改动。
>
> 达成方式三件事：**变更永远向后兼容** → **兼容性全自动挡在合入前** → **发布走灰度通道**。

---

## 0. 名词与分支拓扑

业务 `include` 的引用目标叫 **ref**。分支拓扑在现有 `test`/`main` 基础上只新增一个 `stable`：

| 分支 | 职责 | 业务是否引用 |
|---|---|---|
| `test` | 开发前沿（不变） | 否 |
| `main` | canary 集成线：MR 合入即集成、跑兼容门禁与灰度验证（不变） | 过渡期兼容旧引用 |
| `stable` | **业务唯一推荐引用目标**；只接受 `main` 验证通过后的快进推进 | **是（`ref: stable`）** |

> 建库时 `stable == main`，指向同一 commit，因此存量业务从 `ref: main` 迁到 `ref: stable`
> 行为完全一致，迁移**无紧迫性、无风险**。两者仅在首次「只 promote stable、不直接放行」时分叉。

破坏性大版本（无法兼容消化的变更，一年一两次）另发浮动 tag `v1` / `v2`，多版本并存。

## 1. 变更分类（判断你这次改动要走哪条通道）

| 类型 | 典型例子 | 对业务影响 | 通道 |
|---|---|---|---|
| **A 增量** | 新增能力文件、新增**可选**变量（带安全默认值） | 无 | 自动放行 |
| **B 内部优化** | 重写 `script`、升级镜像 tag、重构内部 `!reference` / includes，**契约不变** | 无 | 兼容门禁通过后自动放行 |
| **C 契约变更** | 变量改名/删除、hidden job 改名/删除、`stage` 变化、产物路径变化、**行为语义变化** | **业务需同步改** | **必须先做兼容消化（第 3 节），否则不得合入** |

**对外契约（= 不可随意改的 API 面）包括：**

1. hidden job 名（`.node-build`、`.pylint` …）
2. `[用户可配]` 变量名与其默认语义
3. job 的 `stage` 归属
4. 产物约定（artifact 路径、dotenv 变量名如 `NEED_BUILD`）
5. 触发规则入口（`.workflow-rules`）

> 内部实现（script 细节、镜像、内部 hidden job、内部变量）**不属于契约**，可自由优化。

---

## 2. 铁律（三条，不可协商）

### 铁律一：契约只增不改（Additive Only）

想优化行为，**加新开关**，默认值保持旧行为：

```yaml
# variables.gitlab-ci.yml
variables:
  QUALITY_SONAR_SCAN_ENGINE: "v1"   # [用户可配] 新引擎上线，默认仍 v1；想尝鲜的业务自行切 v2
```

### 铁律二：必须废弃时，先 alias 内部消化，业务零改动

在保留窗口内（**默认 ≥ 2 个次要版本 / ≥ 60 天**）新旧契约同时可用，只打 `[DEPRECATED]` warning，**不 fail**。三种标准写法见第 4 节。

### 铁律三：C 类变更 = 必须带 alias 方案 + 人工评审

MR 若触及第 1 节列出的对外契约字段，**必须**：

1. 勾选 MR 模板中「契约变更」；
2. 附本次 alias / feature flag 方案；
3. 通过兼容门禁（第 5 节）+ 至少一名维护者评审。

无 alias 且无迁移计划的 C 类变更，门禁直接拦截。

---

## 3. 废弃流程（Deprecation Lifecycle）

```
标记废弃(alias 生效, 打 warning)  ──≥60天/≥2 minor──►  确认使用量归零(雷达遥测)  ──►  移除旧契约
      │                                                      │
      └─ 同时可用, 业务零感知                                  └─ consumers.json 显示 0 引用才允许删
```

- **何时能删**：影响面雷达（`scripts/consumer_radar.py`）产出的 `consumers.json` 显示该旧契约**引用数为 0**，且已过保留窗口。
- **删除本身也是一次 C 类变更**，同样走门禁。

## 4. Alias 标准写法模板（复制即用）

### 4.1 变量改名 —— shell 级回退

```bash
# 新名 NEW_IMAGE_TAG 取代旧名 OLD_IMAGE_TAG，两者都兼容，缺省有默认
IMAGE_TAG="${NEW_IMAGE_TAG:-${OLD_IMAGE_TAG:-default}}"
if [ -n "${OLD_IMAGE_TAG:-}" ] && [ -z "${NEW_IMAGE_TAG:-}" ]; then
  echo "[DEPRECATED] OLD_IMAGE_TAG 将于下个大版本移除，请改用 NEW_IMAGE_TAG"
fi
```

### 4.2 hidden job 改名 —— 转发壳

```yaml
# 新能力
.new-lint:
  stage: lint
  script: [ '...' ]

# 旧名保留为转发壳（继承新能力，仅加一条弃用提示，不改变行为、不 fail）
.old-lint:
  extends: .new-lint
  before_script:
    - echo "[DEPRECATED] .old-lint 将于下个大版本移除，请迁移到 .new-lint"
```

### 4.3 行为语义变化 —— feature flag（默认旧行为）

```yaml
variables:
  FEATURE_NEW_BEHAVIOR: "false"   # [用户可配] 默认关闭=旧行为；业务显式开启才启用新行为
```

```bash
if [ "${FEATURE_NEW_BEHAVIOR}" = "true" ]; then
  : # 新行为
else
  : # 旧行为（默认）
fi
```

> GitLab 15.3 注意：`extends` 对 `allow_failure`、`rules` 等是**覆盖不合并**；alias 转发壳
> 若涉及这些字段需显式复制，避免语义丢失。

## 5. 合入前兼容门禁（Compat Gate，方案心脏）

模板库自身 `.gitlab-ci.yml` 中的 `compat-gate` job（见 `scripts/compat_gate.py`），在 **MR 阶段**执行：

1. 读 `scripts/consumers.json`（雷达产出），抽取 Top N 代表性业务仓（按能力覆盖度抽样）；
2. 将其 `.gitlab-ci.yml` 中 `ref: stable` **文本替换**为当前 MR 分支名（GitLab 15.3 无 `include_ref` 参数，用文本替换法）；
3. 逐个调用**项目级** CI Lint `POST /projects/:id/ci/lint`（能解析 `include:project`）；
4. 进一步做 **merged YAML diff**（本次渲染 vs stable 渲染）自动分类：
   - 完全无变化 → 100% 无影响，自动通过；
   - 仅 `script` / 镜像等内部字段变化 → B 类，自动通过；
   - 契约字段（job 名 / 变量名 / rules / stage）变化 → C 类，MR 评论影响报告，要求 alias 或人工评审。

**任一代表性业务 lint invalid → 门禁 fail，MR 不得合入。**

---

## 6. 发布到 stable（Promote，人工 MR + 门禁）

`stable` 保持 **No one 直推**（谁都不能 `git push`，CI 也不例外），发布统一走与业务仓一致的
「人工 open MR + 门禁绿灯 + 人工合并」通道，**无需任何写/merge token**：

1. **验证**：`main` 分支 pipeline 手动触发 `promote-stable` job，跑 `examples/` 落地的种子项目真实
   pipeline，轮询结果；全绿说明当前 `main` 可发布（任一失败则告警，stable 原地不动，事故半径锁在种子）。
2. **生成发布快照分支**：`bash scripts/release_to_stable.sh`（或按下述规则手动做）。快照分支内容
   = 当前 `main`，但把 **examples + 所有 README** 的 include 引用行 `ref: main` 批量改写为
   `ref: stable`（跳过 BRANCHING.md 等说明性文字），并做改写前后数量校验。
3. **发起 MR**：从快照分支向 `stable` 发起 MR。MR 触发 `.gitlab-ci.yml` 的 **`stable-ref-guard`**
   job（`scripts/check_stable_refs.py`），校验合入内容里 examples + 所有 README 的 include 引用行
   **不得再有 `ref: main`**（红线：stable 分支对外引用恒为 `ref: stable`）。
4. **合并**：`stable-ref-guard` 绿灯后由 Maintainer 点 Merge；合并过程只读校验、不改写任何文件。

> 红线：无论如何合入 stable，`examples/**` 与所有 `README.md` 的 `include ... ref:` 必须是
> `ref: stable`。`stable-ref-guard` 是硬卡点，出现 `ref: main` 引用行即拦截合并。

---

## 7. C 类大版本兜底（唯一需要业务感知的场景）

无法 alias 的破坏性变更发 `v2` tag，并用 codemod 基于 `consumers.json` **自动生成业务仓迁移 MR**
（改 ref、改变量名），**但不自动合并**，留业务 owner 点确认。频率控制在一年一两次。

---

## 8. 维护者检查清单（每个 MR）

- [ ] 已在 MR 模板勾选变更类型（A 增量 / B 内部优化 / C 契约变更）
- [ ] 若为 C 类：已附 alias / feature flag 方案，并保留旧契约 ≥ 60 天
- [ ] `compat-gate` 绿
- [ ] 未删除仍被 `consumers.json` 引用的契约
- [ ] 接入文档 / example 的 include 示例使用 `ref: stable`
