# CI 编排与触发

> 本文档由仓库根 `README.md` 拆分而来，聚焦「CI 编排与触发」。总览与导航见 [README](../README.md)。

## Runner 路由约定

**默认 k8s runner** 具备 tags：`default,cicd,k8s,docker,shared`,已挂载 `/var/run/docker.sock`。绝大多数能力在默认 runner 上运行。

以下能力**必须走专用 runner**（有宿主/GUI/SDK 依赖，无法在 k8s 容器内运行），能力内已默认写好 `tags`,由 GitLab 自动路由：

| 能力 | 默认 tags | 说明 |
|---|---|---|
| `.cocos-build` | `[cocos]` | 依赖 Cocos Creator 编辑器（安装在专用机器） |
| `.cocos-build-windows` | `[cocos, windows]` | Windows 上的 Cocos runner |
| `.msbuild` | `[windows]` | Visual Studio / MSBuild 编译（.NET / C++） |
| `.windows-bat` | `[windows]` | 执行仓库内 .bat 脚本 |

其他能力（lint / review / build/docker / build/nodejs / build/java / …）默认走 k8s runner，无需指定 tags。业务侧如需自定义路由，可在自己的 job 里覆盖 `tags`。


## 触发控制

`.workflow-rules` 提供统一的 pipeline 触发规则，业务侧在自己的 `.gitlab-ci.yml` 里通过 `workflow:` + `!reference` 引入即可：

```yaml
workflow:
  rules:
    - !reference [.workflow-rules, rules]
```

**默认规则**：MR 事件、Tag、默认分支 push 都触发。

**关键字触发**（可选）：如果不希望默认分支的每次 push 都触发构建，可以设置：

```yaml
variables:
  CI_REQUIRE_BUILD_KEYWORD: "true"    # 开启关键字触发
```

设置后，默认分支 push 时 commit message 必须包含 `build` / `smoke` / `release` 任一关键字才触发；否则跳过。

如果想在 pipeline 中间用独立 job 做更灵活的关键字判定（含手动触发 / 自定义关键字集合），改用 `common/.build-filter` 能力 + `NEED_BUILD` dotenv,业务侧下游 job 通过 `rules: - if: '$NEED_BUILD == "true"'` 条件执行。


## 失败允许（卡点控制）

**扫描 / 评审类能力**默认 `allow_failure: true`(失败**不阻断** pipeline,标记 warning,后续 stage 继续)。

业务侧如需让某个能力**变成硬卡点**,在自己的 job 里覆盖 `allow_failure: false` 即可（GitLab CI 的 `extends` 对 `allow_failure` 是**覆盖不合并**）:

```yaml
my-pylint:
  extends: .pylint          # 继承模板的 allow_failure: true (不卡点)
  allow_failure: false      # 覆盖: pylint 失败就阻断 pipeline

my-trivy:
  extends: .trivy
  allow_failure: false      # trivy 变硬卡点

my-eslint:
  extends: .eslint
  # 不写 = 用模板默认（true, 不卡点）
```

**默认 `allow_failure: true` 的能力**：lint / security / quality/sonar / review/ai-review / checks 家族

**默认 `allow_failure: false` 的能力**(硬卡点)：`compliance/*` 系列（合规检测语义就是必须通过）

**更细粒度控制**：`.scan-summary` 提供按严重度阈值判定（`REVIEW_SCAN_FAIL_ON_CRITICAL/MAJOR/MINOR`），独立于 `allow_failure`。

### 合并前扫描卡点（推荐做法）

要实现「扫描通过才能合并」，用 GitLab 原生能力即可，无需外部系统 / 轮询 / 评论：

1. 扫描 job 加 MR 触发 `rules: - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'`，放进 MR pipeline；
2. 扫描 job 覆盖 `allow_failure: false`（扫描失败 → job 失败 → MR pipeline 失败）；
3. 仓库 **Settings → Merge requests → 勾选 "Pipelines must succeed"**（GitLab 依据 MR pipeline 成功与否放行/阻止合并）。

完整组装见 `examples/mr-scan-gate.gitlab-ci.yml`（lint + security + sonar 合并前卡点）。


## 跨 Stage 并发（DAG 模式）

模板里所有**扫描/评审类能力**（lint / sonar / security / ai-review）已内置 `needs: []`（空依赖），让它们**无视 stage 顺序立即启动**，与其他 stage 并发执行。

举例：如果业务 pipeline 有 lint / security / quality / review / build 5 个 stage，前 4 个 stage 的所有 job 会**同时开始跑**，只有 build 类真依赖前置的能力才等。这样 pipeline 总时长 ≈ 最慢单个扫描 job 时长，而不是 4 个 stage 累加。

### 编排规则（业务侧组装时遵循）

`stages:` 只决定 GitLab UI 上的分组显示，**实际执行顺序由 `needs` 决定**。规则：

| 能力类型 | needs 写法 | 说明 |
|---|---|---|
| 扫描/评审（lint/sonar/security/ai）| 已内置 `needs: []` | 源码级，pipeline 起点全并行，无需业务再写 |
| 单测（ut）| 建议显式 `needs: []` | 源码级，与扫描类并行（`ut/go` 未内置，需业务加） |
| build（docker/go/node/cmake…）| `needs: [ut, lint]` | 等质量门禁通过再构建；**只等真依赖的 job** |
| upload（harbor/oss/gitlab）| `needs: [build]` | 依赖 build 产物，**串行** |
| deploy（ssh/gitops/cd）| `needs: [upload]` | 依赖发布产物，**串行** |
| notify | `needs: [最后一个 job]` + `when: always` | 收尾通知，optional 依赖避免上游失败时不发 |

**⚠️ 数据链例外（重要）**：`needs: []` 意味着该 job **不下载任何上游 artifacts**。若某扫描 job 需要消费另一个 job 的产物（如 **sonar 消费 ut 的测试/覆盖率报告** `QUALITY_SONAR_GO_TEST_REPORT`/`_COVERAGE_REPORT`），必须**覆盖**其 `needs: []`，显式声明 needs 那个产物 job，否则拿不到 artifacts：

```yaml
my-unit-test:
  extends: .go-ut
  needs: []            # 源码级，起点并行

my-sonar:
  extends: .sonar-scan
  needs:
    - my-unit-test     # 覆盖能力默认的 needs:[]，串数据链（仍与 lint/ai-review 并行）
```

同理，`.sonar-quality-gate`（读 `.sonar-scan` 产出的 report-task.txt）也须 `needs: [my-sonar]`。

### 典型 DAG 示例

完整的规范编排见 `examples/go-full-pipeline.gitlab-ci.yml`（Go 全链）、`examples/cpp-cmake-build.gitlab-ci.yml`（C++）、`examples/js-full-pipeline.gitlab-ci.yml`（前端）：

```
ut ─┐(needs:[])
lint┤(needs:[]) ──┐
ai ─┘(needs:[])   ├─> build(needs:[ut,lint]) ─> upload(needs:[build]) ─> notify
sonar(needs:[ut]) ┘
```
无依赖的 ut/lint/ai/sonar 起点并行；build 等质量门禁；upload/deploy 串行。

## 定时触发（schedule）

周期性任务（如每周一次的跨仓批量扫描）**不在模板能力内配置 cron**，模板只提供能力，触发时机由业务侧掌握。两步接入：

1. 业务项目 `.gitlab-ci.yml` 的 `workflow.rules` 放行 schedule 事件（通常再放行 `web` 以便手动补跑）：

```yaml
workflow:
  rules:
    - if: '$CI_PIPELINE_SOURCE == "schedule"'
    - if: '$CI_PIPELINE_SOURCE == "web"'
    - when: never          # 该项目只承载定时任务时，其余场景不产流水线
```

2. 项目 **Settings → CI/CD → Pipeline schedules → New schedule**，填 cron。例如每周一 03:00 跑一次：`0 3 * * 1`（时区在该页面单独选择）。

注意事项：

- 定时与手动补跑可能撞车，给 job 加 `resource_group: <name>` 保证同一时刻只跑一个实例。
- schedule 流水线默认跑在计划指定的分支上，与该分支当时的 `.gitlab-ci.yml` 内容一致。
- 定时任务里的 secret 仍走 CI/CD Variables；若变量勾了 **Protected**，计划分支必须是受保护分支才能取到值。
- 完整组装示例见 `examples/active-repos-weekly-scan.gitlab-ci.yml`（每周发现活跃工程/分支并逐工程执行扫描脚本）。
