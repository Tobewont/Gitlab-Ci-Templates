## 设计原则

- **原子能力**：每个 hidden job 只做一件事，业务侧通过 `include` + `extends` 组装完整流水线
- **参数集中管理**：所有可配置项在 `variables.gitlab-ci.yml`；能力内部保持精简
- **默认合理化**：镜像与平台地址使用占位符，凭据走 CI/CD Variables，使用方按环境覆盖
- **跨 stage 并发**：扫描/评审类能力内置 `needs: []`,无视 stage 顺序立即启动，大幅缩短 pipeline 时长；业务侧可在 job 里覆盖 `needs:` 恢复严格顺序
- **失败允许**：扫描/评审类能力默认 `allow_failure: true`(不卡点)；业务侧在自己 job 里覆盖 `allow_failure: false` 即变硬卡点（逐能力独立控制，符合 GitLab 原生语义）
- **国内镜像加速**：由全局开关 `USE_CHINA_MIRROR` 控制（默认 `"true"`）
  - `true`(默认): pip 走阿里云、npm 走 npmmirror、go 走 goproxy.cn、apt 换阿里云 debian 源
  - `false`: 不改各源配置，保持容器/项目原有配置（如镜像内预置的 `.npmrc` / `pip.conf` / `GOPROXY` 环境变量）
  - 业务侧还可显式设置具体变量（`BUILD_NODE_REGISTRY` / `PIP_INDEX_URL` / `BUILD_GO_PROXY`）覆盖到内网私有源
- **业务侧决定组装**：业务侧用 `extends` 继承 hidden jobs，自定义 stages、job 名、`needs`


## 能力清单

### base 层（初始化）
| 能力 | 说明 |
|---|---|
| `.workflow-rules` | 触发规则片段（主分支/Tag 始终构建；关键字触发） |
| `.base-job` | 基础镜像 + locale 初始化 |
| `.base-prepare` | 打印项目/分支/commit/提交信息（诊断） |
| `.pipeline-jobs-fetch` | 脚本片段：`_pipeline_jobs_fetch` 拉取当前 pipeline 全部 job 的 JSON 写入 `JOBS_JSON`（请求失败为 `[]`），供状态聚合类能力复用 |

### common 层（通用底座，无 Git 语义）
| 能力 | 用法 | 说明 |
|---|---|---|
| `.skip-if-disabled` | `!reference` script 片段 | `STEP_ENABLE != true` 时跳过 |
| `.http-download` | script 片段 | 通用 HTTP GET 下载文件（`HTTP_DOWNLOAD_URL` / `HTTP_DOWNLOAD_DEST`） |
| `.http-upload` | script 片段 | 通用 HTTP 上传（form / put 两种模式） |
| `.http-request` | script 片段 | 通用 GET/POST/PUT/DELETE 请求（触发平台 webhook / 调 REST API） |
| `.svn-checkout` | script 片段 | SVN 拉代码（`SVN_REPO_URL` / `SVN_LOCAL_DIR` / 可选用户名密码） |
| `.maven-settings-setup` | `!reference` script 片段 | 生成 `~/.m2/settings.xml`(内网 mirror + 私服凭据；`MAVEN_SERVERS="id=user:pass&id2=user2:pass2"`） |
| `.build-filter` | 独立 job | 按 commit message 关键字（`BUILD_FILTER_KEYWORDS` 逗号分隔）+ 手动触发判断是否需要构建，导出 `NEED_BUILD` dotenv。业务侧下游 job 用 `rules: - if: '$NEED_BUILD == "true"'` 条件执行 |

> **通用 HTTP 能力与协议专属能力的分工**（避免跨层重复选用时困惑）：
> - `common/.http-*`：**通用 HTTP 传输**。走裸 HTTP(S) 协议、无协议专属语义——一次性 webhook 触发、
>   REST API 调用、任意 URL 的文件下载/上传（如拉取业务配置 JSON、触发自研平台接口）。
> - `upload/oss` `download/oss`（对象存储 ossutil）、`upload/ftp`（lftp）、`upload/gitlab`
>   `download/gitlab`（Git 制品仓）、`upload/package` `download/package`（GitLab Package Registry）：
>   **协议/平台专属能力**。有专属认证、重试、manifest、目录枚举等协议语义，制品进出库一律用专属能力，
>   不要用 `.http-*` 自行拼装。
> 
### git 层（Git / GitLab 操作）
| 能力 | 用法 | 说明 |
|---|---|---|
| `.get-changed-files` | `before_script` | 取变更文件，优先级：`CI_CHANGED_FILES` 已有值（上游 `.changes` dotenv 或预定义变量）→ MR 走 GitLab API `/merge_requests/{iid}/changes` → 无 `.git` 工作副本置空跳过 → push/tag 用 `git diff` 两点（浅克隆先 unshallow/deepen）；执行镜像缺 git/curl 时自动经 apk 或 apt 安装（默认换阿里云源，`USE_CHINA_MIRROR=false` 关闭），push 路径仍无 git、MR 路径仍无 curl 则显式报错退出；结果导出到 `CI_CHANGED_FILES` |
| `.filter-changed-files` | `!reference` script 片段 | 按 `STEP_FILE_GLOB` 过滤 `CI_CHANGED_FILES`，输出 `STEP_MATCHED_FILES` |
| `.get-changed-folders` | `!reference` script 片段 | 基于 `CI_CHANGED_FILES` 推断变更的顶层目录（monorepo 场景），输出 `CI_CHANGED_FOLDERS` |
| `.get-mr-diff` | `before_script` | MR 事件时通过 API 拉取各文件 diff，写入 `$GIT_MR_DIFF_FILE` |
| `.git-comment-post` | script 片段 | mr / commit 统一评论发送（`GIT_COMMENT_TARGET` + `GIT_COMMENT_BODY`/`GIT_COMMENT_BODY_FILE`）；guard 拦截时跳过，发送失败 fail-closed |
| `.git-comment` | 独立 job | `.git-comment-post` 的即用封装（纯 API 调用，`GIT_STRATEGY: none` 不拉源码） |
| `.close-mr` | script 片段 | 通过 GitLab API 关闭当前 MR（`state_event=close`），可选附加 `GIT_MR_CLOSE_COMMENT` |
| `.merge-mr` | script 片段 | 通过 GitLab API 合并当前 MR（`PUT /merge`）；可选 `GIT_MR_MERGE_WHEN_PIPELINE_SUCCEEDS`（配合 Pipelines must succeed 成功后自动合并）/ `GIT_MR_MERGE_REMOVE_SOURCE_BRANCH` / `GIT_MR_MERGE_SQUASH` / `GIT_MR_MERGE_COMMIT_MESSAGE`；合并被拒（pipeline 未成功/冲突/无权限）即失败 |
| `.git-https-auth` | `before_script` | 为 Git HTTPS 配置认证（`GIT_HTTPS_DOMAIN` / `GIT_HTTPS_USERNAME` / `GIT_HTTPS_TOKEN`，默认引用 base），后续 clone / go module / 私有依赖复用 |
| `.git-describe` | 独立 job | 生成应用版本号，dotenv 导出 `CI_APP_VERSION` 给下游 job 消费（支持 git-describe / commit-sha / tag-or-sha 三种策略） |
| `.get-commit-keyword` | 独立 job | 扫描本次 push 的 commit message，返回首个包含 `COMMIT_KEYWORD` 的完整消息到 `CI_MATCHED_COMMIT_MESSAGE` |
| `.changes` | 独立 job（stage `.pre`） | 变更文件统一计算一次并 dotenv 下发，下游 `.get-changed-files` 检测到已有值自动跳过重复计算 |
| `.submodule-checkout` | `before_script` | 私有子模块检出（`GIT_SUBMODULE_DOMAIN` / `GIT_SUBMODULE_USERNAME` / `GIT_SUBMODULE_TOKEN` 默认引用 base，重写 https/http/ssh 地址后递归拉取） |
| `.mr-verdict` | 独立 job（`when: always`） | MR 检测结论：汇总本 pipeline 各 job 状态，按 `allow_failure` 泛化判定是否有被拦截的必检项（仅 `allow_failure=false` 且 failed/canceled 计入 blocked），复用 `.git-comment-post` 回帖；`GIT_MR_VERDICT_AUTO_CLOSE=true` 时对有拦截项的 MR 执行关闭；`GIT_MR_VERDICT_EXTRACT` 可对失败关注 job 从日志提取明细附到评论 |
| `.git-job-log` / `.git-job-log-job` | `!reference` 片段 / 独立 job | 按 job 名拉取 CI 日志并提取内容（MATCH 命中 / EXCLUDE 丢弃 / STRIP 清洗正则，去 ANSI、去重、限量、JOINER 拼接写 OUTPUT）；各工具（prettier/eslint/clang 等）只换正则、无需各写脚本 |

> git 层能力已按 `changed-files / mr / mr-verdict / comment / job-log / auth / version` 子目录拆分；`git/jobs.gitlab-ci.yml`
> 与 `git/variables.gitlab-ci.yml` 保留为聚合入口。
> commit 评论用 `.git-comment-post` + `GIT_COMMENT_TARGET=commit` + `GIT_COMMENT_BODY`。

### notify 层（通知）
| 能力 | 说明 |

| `.notify-base` | 公共基座：查 pipeline 状态、组装标题/正文、JSON 转义（不直接使用，由 `.notify-*` 通过 `extends` 继承） |

| `.notify-feishu-bot` | 与 `.notify-feishu` 相同 |
| `.notify-wework` | 企业微信自定义群机器人；支持 `NOTIFY_WEWORK_MENTIONED_MOBILES`(手机号 / @all) |
| `.notify-dingtalk` | 钉钉自定义群机器人；可选 `NOTIFY_DINGTALK_SIGN_SECRET` 加签、`@` 手机号 / @全体 |
| `.notify-webhook` | POST `{"text": "<标题与正文>"}` 到 `NOTIFY_WEBHOOK_URL` |
| `.notify-inline` | 放进 `after_script`。状态：`NOTIFY_STATUS_OVERRIDE`，否则 `CI_JOB_STATUS`；该值为 running 或空时读 `.notify-status`，没有则记失败 |
| `.notify-preheat` | 预告通知。默认阶段 `.pre`，不查状态。文案用 `NOTIFY_PREHEAT_*`，渠道 `NOTIFY_PREHEAT_CHANNEL` |
| `.notify-restart-notice` | `.notify-preheat` 的「服务重启」场景别名：文案由 `NOTIFY_RESTART_SERVICE` / `_LEAD_MINUTES` / `_VERSION` 组装 |

**两种用法**：

1. **聚合入口 `.notify`**：一个 job 内单选或多选串行发送
   ```yaml
   my-notify:
     extends: .notify
     variables:
       NOTIFY_CHANNEL: "feishu,wework"   # 单个或多个（逗号分隔），best-effort 串行
   ```
2. **独立能力 `.notify-<channel>`**：多个 job 并发发送，可放在不同 stage / 依赖不同前置 job
   ```yaml
   my-notify-feishu:
     extends: .notify-feishu
   my-notify-wework:
     extends: .notify-wework
   ```

**pipeline 聚合状态判定（避免收尾 job 误报）**：`.notify`（`NOTIFY_STATUS_SOURCE=pipeline`，默认）判定整体状态时会拉取本 pipeline 全部 job 聚合，并**排除自身与收尾类 job**（`NOTIFY_EXCLUDE_JOBS_REGEX`，默认 `^(notify.*|mr-verdict|scan-summary.*)$`）——因为 `notify` 常与 `mr-verdict` / `scan-summary` 同处收尾阶段并发，若把尚在 running 的收尾 job 计入，会把整体误判为 running 进而误报「失败」。失败/取消只看被排除后的「实质」job；聚合仍为 running 时按 `NOTIFY_WAIT_TERMINAL_RETRIES`（默认 6）× `NOTIFY_WAIT_TERMINAL_INTERVAL`（默认 3s）有界轮询，等实质 job 进入终态。轮询结束仍只有收尾 job 在跑、且没有失败或取消时，状态记为成功。耗时取这些实质 job 最早开始到最晚结束的秒数，含 job 之间的空隙。成功且有发布记录时，默认正文在【项目】后插入【制品】；失败、取消、跳过不插入。

**自定义消息模板**：优先级 `NOTIFY_TITLE_TEMPLATE` / `NOTIFY_MSG_TEMPLATE` 显式设置 > `NOTIFY_SCENARIO` 场景默认 > `pipeline` 兜底。

**场景化默认模板**（`NOTIFY_SCENARIO`）：一行选择内置文案，无需自己写模板

| SCENARIO | 默认标题 | 默认消息字段 |
|---|---|---|
| `pipeline`(默认) | `${EMOJI} 流水线${STATE}` | 项目/分支/Commit+Title/作者/触发人/状态(含耗时)/流水线 URL |
| `build` | `${EMOJI} 构建${STATE}` | 项目/分支/Commit+Title/作者/触发人/状态(含耗时)/流水线 URL |
| `deploy` | `${EMOJI} 部署${STATE}` | 公共字段 + 【环境】 |
| `scan` | `${EMOJI} 代码扫描${STATE}` | 项目/分支/Commit+Title/作者/触发人/状态(含耗时)/流水线 URL |
| `review` | `${EMOJI} 代码评审${STATE}` | 公共字段 + 【MR】(!IID 标题 源→目标分支) |
| `compliance` | `${EMOJI} 合规检测${STATE}` | 项目/分支/Commit+Title/作者/触发人/状态(含耗时)/流水线 URL |
| `smoke` | `${EMOJI} 冒烟测试${STATE}` | 项目/分支/Commit+Title/作者/触发人/状态(含耗时)/流水线 URL |

**用法**:

```yaml
# 场景化（推荐，一行搞定）
my-scan-notify:
  extends: .notify
  variables:
    NOTIFY_SCENARIO: "scan"

# 完全自定义（覆盖场景默认）
my-notify:
  extends: .notify
  variables:
    NOTIFY_TITLE_TEMPLATE: "镜像制作${STATE}"
    NOTIFY_MSG_TEMPLATE: "【项目】$CI_PROJECT_NAME\n【镜像】registry.example.com/aaa:$CI_COMMIT_SHORT_SHA\n【状态】$STATUS"
```

模板支持 `$STATUS` / `$EMOJI` / `$STATE` / `$COMMIT_TITLE`(commit message 首行) 及任意 GitLab CI 变量;`\n` 表示换行。

**多点通知**（同一 pipeline 多 stage 分别发通知）:

两种方式各有场景：

- **方案 A（独立 notify job + 查上游 job 状态）**——需要严格 stage 隔离、需要在专用 stage 汇总时用

  ```yaml
  notify-sonar:
    extends: .notify
    stage: notify-quality
    needs: [my-sonar]
    when: always                      # sonar 失败也发
    variables:
      NOTIFY_SCENARIO: "scan"
      NOTIFY_STATUS_SOURCE: "job"     # 查 my-sonar 状态而非 pipeline
      NOTIFY_UPSTREAM_JOB: "my-sonar"
  ```

- **方案 C（`after_script` 内嵌 `.notify-inline`）**——轻量场景，在任意 job 末尾追加通知

  ```yaml
  my-sonar:
    extends: .sonar-scan
    variables:
      NOTIFY_SCENARIO: "scan"
    script:
      - !reference [.sonar-scan, script]
      - echo success > .notify-status    # 显式声明本 job 成功
    after_script:
      - !reference [.notify-inline, script]
  ```

  **状态判定**：`NOTIFY_STATUS_OVERRIDE` > `CI_JOB_STATUS` 为 success / failed / canceled / skipped > `.notify-status` > 记失败。`CI_JOB_STATUS` 在 `after_script` 里仍是 running 或空时，才读 `.notify-status`。script 末尾可写 `echo success > .notify-status`，或 `!reference [.notify-mark-success, script]`。

  内嵌通知同样支持 `NOTIFY_CHANNEL` 多渠道、场景化模板、自定义模板变量。

完整示例见 `examples/multi-point-notify.gitlab-ci.yml`。

**预告通知（`.notify-preheat` / `.notify-restart-notice`）**

在流水线一开始播报「接下来会发生什么」，例如服务即将重启：

```
【重启预告】测试环境的 api-service 服务（版本 1.2.3）（服务组 group-a）将在 5 分钟后重启，请注意检查。
```

与 `.notify` / `.notify-inline` 的区别：

| 维度 | `.notify` / `.notify-inline` | `.notify-preheat` |
| --- | --- | --- |
| 触发时机 | 所在阶段结束时 | 默认 `.pre`，可改 `stage` |
| 状态判定 | 查 pipeline / job 状态 | 不查状态，不参与状态聚合 |
| 消息形态 | 纯文本，正文含流水线地址 | 纯文本 |
| 渠道变量 | `NOTIFY_CHANNEL` | `NOTIFY_PREHEAT_CHANNEL` |
| 支持渠道 | feishu / wework / dingtalk / webhook | 同上，地址共用各渠道 webhook |

```yaml
restart-notice:
  extends: .notify-restart-notice
  variables:
    NOTIFY_RESTART_SERVICE: "api-service"
    NOTIFY_RESTART_LEAD_MINUTES: "5"

preheat-notice:
  extends: .notify-preheat
  variables:
    NOTIFY_PREHEAT_TEXT: "本次将更新配置，预计 3 分钟内完成"
```

| 变量 | 默认 | 说明 |
| --- | --- | --- |
| `NOTIFY_PREHEAT_ENABLE` | `true` | 开关 |
| `NOTIFY_PREHEAT_TEXT` | 空 | 预告正文；留空则按「服务重启」场景自动组装 |
| `NOTIFY_PREHEAT_EXTRA_TEXT` | 空 | 追加到正文末尾（换行拼接） |
| `NOTIFY_PREHEAT_TITLE` | 空 | 标题；留空为「<服务名> 重启预告」 |
| `NOTIFY_PREHEAT_ENV_TEXT` | `测试环境` | 环境文案 |
| `NOTIFY_PREHEAT_CHANNEL` | `feishu` | `feishu` / `wework` / `dingtalk` / `webhook`，可逗号多选 |
| `NOTIFY_PREHEAT_STRICT` | `false` | `true` 时地址为空或发送失败则 job 失败 |
| `NOTIFY_RESTART_SERVICE` | 空 | 服务名；留空回退 `CI_PROJECT_NAME` |
| `NOTIFY_RESTART_LEAD_MINUTES` | `5` | 提前多少分钟播报（正整数，非法则 job 失败） |
| `NOTIFY_RESTART_VERSION` | 空 | 版本号；留空且未配源码宏时，文案不含版本 |
| `NOTIFY_PREHEAT_MACRO_FILE` | 空 | 版本号兜底：源码宏文件路径，如 `include/version.h` |
| `NOTIFY_PREHEAT_MACRO_VERSION` | 空 | 版本号兜底：宏名，如 `APP_VERSION` |

文案中的服务组取 `NOTIFY_PREHEAT_SVRGROUP`；未配置时文案不含服务组。

预告只发文案，不会让流水线等待 N 分钟；需要等待请在使用方流水线里加延时 job。

### scan 层（跨仓批量扫描调度）
| 能力 | 说明 |
|---|---|
| `.active-repos-discover` | 只读 GitLab API 发现活跃工程与活跃分支。范围：`SCAN_ACTIVE_GROUPS`（留空=全局扫描 token 可见工程，默认；指定=仅这些 group）；工程：`SCAN_ACTIVE_PROJECT_TOP_N`（`0`=全部活跃工程，默认；`N`=最活跃前 N 个）；分支：`SCAN_ACTIVE_BRANCH_TOP_N`（`1`=仅默认分支，默认；`0`=全部活跃分支；`N>1`=默认分支+最活跃(N-1)个）；窗口天数由 `SCAN_ACTIVE_WINDOW_DAYS`（默认 7）控制。产出 `active-repos.json` 与 `SCAN_ACTIVE_PROJECT_COUNT`（工程数）/ `SCAN_ACTIVE_TARGET_COUNT`（工程+分支组合数）dotenv（`GIT_STRATEGY: none`，不需源码） |
| `.active-repos-scan` | 消费清单，逐「工程+分支」组合 clone 后在工程根目录执行 `SCAN_ACTIVE_NPX_CMD`；每组合独立进程 + 硬超时、独立工作目录与日志（名含分支），组合间失败隔离，末尾统一汇总并产出结果 JSON 与各组合日志 |

> 只做调度：扫描规则、结果处理与上传由 `SCAN_ACTIVE_NPX_CMD` 指向的 npx 包自身实现。
> 定时（如一周一次）不在能力内配置，由业务侧 `workflow.rules` 放行 `$CI_PIPELINE_SOURCE == "schedule"`
> + 项目 Pipeline schedules 的 cron 完成；组装示例见 `examples/active-repos-weekly-scan.gitlab-ci.yml`。
> 分支选取是「默认分支保底 + 其余按活跃度补齐」，不是单纯取提交数前 N：某工程默认分支仅 3 次提交、另有 dev(30)/qa(18) 时，`BRANCH_TOP_N=2` 选中默认分支 + dev。默认分支窗口内无提交则不占名额，`BRANCH_TOP_N=1` 时该工程整体跳过。`BRANCH_STRATEGY=default-branch` 等价 `BRANCH_TOP_N=1`。
> 工程活跃度 = 其窗口内提交数最多的那个分支的提交数（与该分支是否入选无关），并列时最后活动时间更新者优先；`SCAN_ACTIVE_PROJECT_TOP_N=0` 表示窗口内全部活跃工程。
> `SCAN_ACTIVE_MAX_PROJECTS` 是拉取阶段按最后活动时间的硬上限（安全阀），`SCAN_ACTIVE_PROJECT_TOP_N` 是统计完提交数后按真实活跃度的择优截断，两者可同时生效。
> 工程/分支 Top N 生效时同一工程会产出多条记录（`branch_rank` 1..N），各组合独立 clone、独立执行、独立计入汇总；实际数量不足 N 时取实际数量。下游 `rules` 判空用 `SCAN_ACTIVE_TARGET_COUNT`。
> 默认 `SCAN_ACTIVE_FAIL_ON_ERROR: "false"`（失败只记录不阻断），需要卡点时业务侧覆盖为 `"true"`。

三种能力统一输出 `DOWNLOAD_OUTPUT_DIR`、`DOWNLOAD_FILE_COUNT`、`DOWNLOAD_MANIFEST_FILE`，并为每个
文件记录相对路径、大小和 SHA-256。完整参数见各目录 `variables.gitlab-ci.yml`，组装示例见
`examples/download-artifacts.gitlab-ci.yml`。

> download 能力以 jq 1.3 为最低版本，不使用 `--argjson`、`all()`、
> `startswith()`、`test()`、`gsub()`、`--slurpfile` 等新版本语法。

### deploy 层（部署到运行环境）

## 参数约定

所有能力参数都集中在对应模块的 `variables.gitlab-ci.yml`,用注释标注：
- `# [用户可配]` — 业务侧可在 GitLab CI/CD Variables 或 `.gitlab-ci.yml` 覆盖
- `# [内部]` — 能力实现细节，一般不需要业务侧关心

**通用步骤参数**（`common/variables.gitlab-ci.yml`）供能力组装用：

| 变量 | 类型 | 用途 |
|---|---|---|
| `STEP_ENABLE` | 用户可配 | 是否启用该步骤 |
| `STEP_NAME` | 内部 | 日志显示名 |
| `STEP_FILE_GLOB` | 内部 | 变更文件过滤正则（如 `.pylint` 恒为 `\.py$`） |
| `STEP_ARTIFACT` | 内部 | 产物路径（跳过时写空数组占位） |
| `STEP_MATCHED_FILES` | 运行时 | `.filter-changed-files` 输出的匹配文件列表 |
