# GitLab CI 公共模板仓库 · 对接使用文档

> 仓库路径示例：`group/gitlab-ci-templates`
> 定位：只提供**通用原子能力**，不含业务组装。业务项目通过 `include` + `extends` + 变量覆盖，组合出自己的流水线。

---

## 1. 总体设计

```
业务项目 .gitlab-ci.yml
    │  include: project/ref/file（可多个）
    ▼
模板原子能力（隐藏 job，以 . 开头，如 .node-build / .eslint / .docker-build）
    │  extends + variables 覆盖
    ▼
业务 job（可见，决定何时跑、跑什么场景、成功失败如何通知）
```

三个核心机制：

| 机制 | 说明 |
|---|---|
| `include` | 按需引入能力文件，每个能力是独立 yml，互不影响 |
| `extends` | 业务 job 继承隐藏 job，只覆盖差异字段（`allow_failure`、`tags` 等是**覆盖不合并**） |
| 变量驱动 | 每个能力目录下 `variables.gitlab-ci.yml` 声明默认值 + 注释，业务侧同名变量覆盖即完成配置，**不需要改模板** |

## 2. 目录结构

```
base/            全局变量（USE_CHINA_MIRROR 等）与公共 job
common/          通用片段（workflow-rules 触发规则、build-filter 关键字构建）
lint/            代码检查：js / go / python / cpp / lua / php
review/          AI 代码评审（review/ai）、扫描汇总（scan-summary）
quality/         SonarQube 扫描与上报
security/        安全扫描（Trivy、JFrog Xray 等）
scan/            跨仓批量扫描调度（active-repos：活跃工程/分支发现 + 逐工程执行扫描脚本）
compliance/      合规检测（含 go 专项）
ut/              单元测试：go / python
build/           构建：nodejs / go / java / cpp / android / docker / protobuf / windows / game(cocos)
deploy/          部署：ssh / gitops / cd
upload/          制品上传：harbor / oss / ftp / package / gitlab
notify/          通知：webhook / 钉钉 / 飞书 / 企业微信
git/             git 辅助能力
checks/          杂项检查
examples/        组装示例（js/go/cpp/android/部署/通知/安全…），**接入时先抄最接近的示例**
```

命名约定：

- 能力文件：`jobs.gitlab-ci.yml`（隐藏 job）+ `variables.gitlab-ci.yml`（默认变量与注释）
- 隐藏 job 以 `.` 开头（如 `.node-build`），不会单独运行；业务 job `extends` 后才是真实 job
- 变量带能力前缀：`BUILD_NODE_*`、`BUILD_DOCKER_*`、`LINT_JS_*`、`QUALITY_SONAR_*`、`NOTIFY_*`、`SCAN_ACTIVE_*`

## 3. 快速接入（5 步）

1. **找示例**：`examples/` 里挑一份最接近的（如前端项目 → `js-full-pipeline.gitlab-ci.yml`）。
2. **include 能力**：

```yaml
include:
  - project: 'group/gitlab-ci-templates'
    ref: stable                     # 推荐引用 stable（经兼容门禁+灰度验证的稳定线）；详见 docs/发布与兼容契约.md
    file: 'lint/js/jobs.gitlab-ci.yml'
  - project: 'group/gitlab-ci-templates'
    ref: stable
    file: 'build/nodejs/jobs.gitlab-ci.yml'
  - project: 'group/gitlab-ci-templates'
    ref: stable
    file: 'build/docker/jobs.gitlab-ci.yml'
  - project: 'group/gitlab-ci-templates'
    ref: stable
    file: 'notify/jobs.gitlab-ci.yml'
```

3. **定触发规则**（推荐复用模板统一规则）：

```yaml
workflow:
  rules:
    - !reference [.workflow-rules, rules]   # 默认：MR / Tag / 默认分支 push 触发
```

4. **覆盖变量**（看对应能力目录的 variables 文件，按需覆盖）：

```yaml
variables:
  USE_CHINA_MIRROR: "true"          # true=模板显式设国内源(npmmirror 等); false=保持镜像默认
  BUILD_NODE_ENABLE: "true"
  BUILD_NODE_IMAGE: "registry.example.com/library/node:24"
  BUILD_NODE_BUILD_CMD: "npm run build"
  BUILD_DOCKER_IMAGE_NAME: "myapp/service"
  BUILD_DOCKER_REGISTRY: "registry.example.com"
  NOTIFY_CHANNEL: "feishu"
```

5. **组装 job**：

```yaml
node-build:
  extends: .node-build
  rules:
    - if: '$CI_PIPELINE_SOURCE == "push" && $CI_COMMIT_BRANCH =~ /^(test|main|master)$/'
  variables:
    NOTIFY_SCENARIO: "build"

docker:
  extends: .docker-build
  needs: [node-build]               # DAG 并发，不等整个 stage
  variables:
    NOTIFY_SCENARIO: "build"
```

## 4. 关键约定

### 4.1 Runner 路由

- 绝大多数能力跑在**默认 k8s runner**（tags: `default,cicd,k8s,docker,shared`，已挂 docker.sock），业务无需关心。
- 以下能力必须走**专用 runner**（模板内已写好 tags，自动路由）：

| 能力 | tags | 依赖 |
|---|---|---|
| `.cocos-build` / `.cocos-build-windows` | `[cocos]` / `[cocos, windows]` | Cocos Creator 编辑器 |
| `.msbuild` / `.windows-bat` | `[windows]` | Visual Studio / .bat |

### 4.2 触发控制

- 默认规则：MR 事件、Tag、默认分支 push。
- 关键字触发：`CI_REQUIRE_BUILD_KEYWORD: "true"` 后，默认分支 push 的 commit message 需含 `build` / `smoke` / `release` 才触发。
- 更细粒度：用 `common/.build-filter` + `NEED_BUILD` dotenv，下游 job `rules: - if: '$NEED_BUILD == "true"'`。

### 4.3 失败允许（卡点）

- 扫描/评审类默认 `allow_failure: true`（不阻断）。
- 业务 job 里写 `allow_failure: false` 即变硬卡点（覆盖不合并）。

### 4.4 国内镜像开关

`USE_CHINA_MIRROR`（base 默认 `"true"`）控制 go/java/nodejs/python/git 等模板是否切国内源（goproxy.cn、npmmirror、阿里 pip/apt 源）：

- `"true"`：模板显式 `npm config set registry https://registry.npmmirror.com` 等。
- `"false"`：模板**不改任何源**，保持镜像/项目默认配置。
- 若某个源要自定义，用各能力的显式变量（如 `BUILD_NODE_REGISTRY`），优先级高于开关。

### 4.5 通知

`notify/jobs.gitlab-ci.yml` 提供 `.notify-inline`（after_script 内联通知），按 `NOTIFY_SCENARIO` 选文案模板：

| scenario | 用途 | 标题 |
|---|---|---|
| `build` | 构建/制品 | 🛠 项目 构建成功/失败 |
| `deploy` | 部署 | 🚀 项目 部署… |
| `scan` | 代码扫描 | 🔍 |
| `review` | 代码评审 | 📝 |
| `compliance` / `smoke` / `pipeline` | 合规 / 冒烟 / 通用 | — |

状态行格式统一为 `【状态】<job名>阶段 成功/失败`。推荐写法（自带状态判定）：

```yaml
script:
  - echo failed > .notify-status
  - !reference [.node-build, script]
  - echo success > .notify-status
after_script:
  - !reference [.notify-inline, script]
```

> `.notify` 与 `.notify-inline` 通过 `!reference` 复用同一份 `.notify-build-message` 组装编排；文案按场景拆在 `notify/message/<场景>.gitlab-ci.yml`，改某场景文案只改对应文件。
> 飞书、企微、钉钉和通用 webhook 都是机器人直连，地址放在对应的 `*_WEBHOOK_URL`。详见 [通知渠道对接](通用通知服务对接.md)。

### 4.6 Secret 管理

敏感值（token、key）一律走 GitLab **CI/CD Variables** 注入（Settings → CI/CD → Variables，masked/protected），不要写进 yml 或模板。模板只引用变量名。

| Secret | 用途 |
|---|---|
| `GITLAB_TOKEN` | 通知查 pipeline/job 状态。`.notify-base` 读取 `NOTIFY_GITLAB_TOKEN`，默认值是 `GITLAB_TOKEN` |
| `NOTIFY_FEISHU_WEBHOOK_URL` | 飞书自定义机器人地址 |
| `NOTIFY_WEWORK_WEBHOOK_URL` | 企业微信群机器人地址 |
| `NOTIFY_DINGTALK_WEBHOOK_URL` | 钉钉自定义机器人地址 |
| `NOTIFY_WEBHOOK_URL` | 通用 webhook 地址 |
| `HARBOR_USERNAME` + `HARBOR_PASSWORD` | 推送镜像到镜像仓库 |

## 5. 接入常见坑（FAQ）

1. **npm install 报 `Cannot convert undefined or null to object` / ETARGET**
   npm 7+ 遇到 npm6 老 lockfile 会全量回源拉 metadata；若依赖里有已被 registry 封禁/下架的包（如 vab 系），会直接崩。对策：镜像预置 node_modules + `--prefer-offline`，或升级 lockfile，或换内网代理源。
2. **镜像预置 node_modules 的项目，记得关模板缓存**
   模板 `cache: [node_modules/, .npm/]` 会在 job 前恢复旧 node_modules，导致 `mv /root/node_modules ./` 嵌套失效（变成 `node_modules/node_modules`）。业务 job 加 `cache: []` 覆盖。
3. **构建被 `Killed`（OOM）**
   `BUILD_NODE_MAX_OLD_SPACE_SIZE` 给的是堆上限，webpack 还有堆外开销。堆 16G 需要 pod limit ≥ 20Gi，否则调小堆（如 12288）。
4. **include 了但 job 没跑**：检查 `workflow.rules` 与 job 自身 `rules` 的交集；MR 流水线里 push-only 的 job 不会出现。
5. **改模板变量不生效**：业务侧同名变量会覆盖模板默认值，确认拼写与前缀。
6. **飞书通知发不出**：确认 CI/CD Variables 已注入 `NOTIFY_FEISHU_WEBHOOK_URL`。开启签名校验时再填 `NOTIFY_FEISHU_SIGN_SECRET`。详见 [通知渠道对接](通用通知服务对接.md)。

## 7. Git 拉取深度与跳过克隆

模板默认 `GIT_DEPTH: "1"`（浅克隆）。按需调整：

- **需要 git 历史**（`.git-describe` 用 `git describe --tags` 生成版本号）：job 级覆盖
  ```yaml
  my-version-job:
    variables:
      GIT_DEPTH: "0"
  ```
  或改用 `GIT_VERSION_STRATEGY: tag-or-sha / commit-sha`。
- **不需要源码的 job**（纯调 API、只消费上游 artifacts）：job 级跳过克隆
  ```yaml
  my-api-job:
    variables:
      GIT_STRATEGY: none
  ```
  `.notify` / `.close-mr` / `.deploy-cd` 已内置跳过。
- **其余 job 保持默认**：`.get-changed-files` 已有 `CI_CHANGED_FILES` 时直接使用；否则 MR 走 MR API，无 `.git` 工作副本则跳过，push/tag 用 `git diff` 两点（浅克隆先 unshallow，未完成时 `fetch --deepen=50`）。`.get-commit-keyword` 在 before_sha 不可达时只看当前 commit。

## 8. CI 配置防合并覆盖（.ci-config-guard）

约定：`.gitlab-ci.yml` 只允许**直接 push** 到分支修改；任何 MR 合入若改动了它，
说明会用源分支内容覆盖目标分支（git 三方合并对单方修改静默采纳，merge=ours 管不到）。

接入：挂 `.ci-config-guard`，并确保项目开启 **All pipelines must succeed**；
同时 workflow rules 必须放行 MR 事件（guard 仅存在于 MR 流水线；不放行则 MR 不产生流水线、guard 无卡点）：

```yaml
workflow:
  rules:
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
    - if: '$CI_COMMIT_BRANCH && $CI_OPEN_MERGE_REQUESTS'
      when: never
    - if: '$CI_COMMIT_BRANCH'

ci-config-guard:
  extends: .ci-config-guard
```

行为：MR 流水线中，源分支相对合并基点改动 `CHECKS_CI_CONFIG_GUARD_PATHS`
（默认 `.gitlab-ci.yml`，可空格分隔配多个）则 job 失败卡死合并；push/tag 流水线
rules 直接排除本 job（不创建，下游零等待），而非运行时跳过。
改 CI 配置请直接 push 到目标分支，或 MR 先合入代码、再单独推配置。

开关：`CHECKS_CI_CONFIG_GUARD_ENABLE`（默认 `"true"`，启用拦截）。显式设为 `"false"`
（项目 CI/CD Variables 或 .gitlab-ci.yml 顶层 variables）时 guard job **不创建**（rules 级），
needs 它的各 job 经 optional 自动豁免、零等待——guard 完全退出，不作任何 job 的前提。

guard 不过则任何 job 不启动（三道闸门）：
1. 检查/扫描类原子能力（checks/lint/security/quality/review 下各 job）均
   `needs: [ci-config-guard(optional)]`：guard 失败一律不启动；未接入 guard 的流水线自动豁免。
2. 其余无 needs 的 job（build/notify/汇总等）由 stage 顺序天然阻塞——guard 位于内置 `.pre` 阶段，
   它失败则后续 stage 的 on_success job 全部不启动。
3. `when: always` 的模板 job（notify、scan-summary）无法被 needs/stage 拦截（GitLab 语义），
   启动后读取 guard 状态文件（`.ci-config-guard-result`，随 artifacts 传递）立即退出，
   不执行实质工作、不发送通知。
注意：接入时 job 名必须叫 `ci-config-guard`（needs 按名匹配）；
业务自定义 job 若自写 `needs` 或 `when: always` 则不受前两者约束。
